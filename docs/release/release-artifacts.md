## Release notes (draft)

**AIGov Core, release candidate (controlled pilot).**

Security fixes:

- Execution receipts are accepted only from an authenticated executor principal, and only for an authorization Core issued in the same run.
  Previously any key could record a receipt for an authorization that was never issued.
- Production refuses to start without authenticated principals (`GOVAI_PRINCIPALS_JSON` or OIDC). Previously it started without them, so any key
  could post approvals and receipts.
- Crash-point instrumentation is a non-default `fault-injection` Cargo feature. A normal build contains no crash code and refuses to start if the
  fault-injection variables are set.

Fixes:

- The SDK wheel now includes the PostgreSQL executor schema (`migrations/pg/0001_executor_pg.sql`). Downstream installs could not apply it before.
- `ai_discovery_reported` is allowed for the agent role. Before this, no role could post it when principals were configured.

Behaviour changes that affect integrations:

- A client that posts `execution_receipt` without an executor key is refused with `RECEIPT_REQUIRES_EXECUTOR` (403).
- A receipt that names an authorization Core did not issue for the run is refused with `RECEIPT_FOR_UNISSUED_AUTHORIZATION` (422).
- Production without principals is refused at start.

Verification added: crash consistency at three issuance boundaries, two-process single use of an approval, receipt provenance, production
principal refusal, the wheel contents, and a two-instance ledger test.

Known limitations: see the residual risks R-1 to R-11 in the report.

## Versioning recommendation

Reconciled facts (checked on this branch):

- `rust/Cargo.toml` and `python/pyproject.toml` both declare `0.2.1`, and so does `CHANGELOG.md`'s latest release, `[0.2.1] - 2026-06-10`.
- Tag `v0.3.0-core-replay-operations` exists, but its own `Cargo.toml` declares `0.2.1` and its changelog has no `0.3.0` section. The tag names a
  milestone, not a version.
- Tag `v1` is the staging promotion commit (`release: promote staging to main (#161)`), and it also declares `0.2.1`.
- Tags `v0.1.0-core-public` and `v0.2.0-core-runtime-foundation` are older milestones with the same pattern.

**Recommendation: `0.4.0-rc.1`** (Python: `0.4.0rc1`, the PEP 440 form). The changes since `0.2.1` break integrations: receipts need an executor, staging and
production need principals, and the role rule changes what each key may post. Pre-1.0, that is a minor bump. `0.3.0` is avoided because the tag
`v0.3.0-core-replay-operations` already uses that number for a different milestone.

The version is **not changed in this branch**. A bump touches pinned tests and CI, which is more churn than the decision warrants before the owners choose.
Every place that must change together:

- `rust/Cargo.toml` (`version`), and `rust/Cargo.lock` (regenerated by `cargo build`);
- `python/pyproject.toml` (`version`, PEP 440 form);
- `CHANGELOG.md`: rename `[Unreleased]` to `[0.4.0-rc.1] - <date>` and add a fresh `[Unreleased]`;
- `python/tests/test_validate_changelog.py` (`latest_released`), `python/tests/test_generate_release_notes.py` (`render_release_notes("0.2.1", …)`);
- `python/tests/test_experiments.py` and `python/aigov_py/experiments/real_world_ci_runner.py`, which pin `aigov-py==0.2.1` in a generated CI snippet;
- `python/tests/test_runtime_diagnostics_cli.py` (`runtime_version`).

Tagging is a separate decision, and the existing tags are not moved or deleted. The owners decide whether the old tags remain as milestone markers.

## Software bill of materials

Method: the inventory is the lockfile content, not a signed or generated CycloneDX document.

- `docs/evidence/release-candidate/sbom/aigov-core-rust.cdx.json`: CycloneDX 1.5, 327 registry crates with their lockfile SHA-256 (generated by
  `scripts/generate_sbom.py`). Not validated against the official schema.
- `docs/evidence/release-candidate/sbom/aigov-py-python.cdx.json`: CycloneDX 1.5, the 37-package closure of `aigov-py`. Installed metadata carries no hashes.
- `docs/evidence/release-candidate/provenance.json`: source commit, toolchains, digest-pinned base images, and artifact SHA-256 values, from
  `scripts/release_provenance.py`. Not signed.
- `docs/evidence/release-candidate/python-dependencies.txt`: the six declared Python runtime dependencies with their version floors. There is no
  Python lockfile, so transitive Python dependencies are not pinned by this repository.

Not done: a vulnerability scan of this inventory (the CI `cargo-audit` and `pip-audit` jobs run on the PR), a signed SBOM, and a reproducible-build
comparison (R-10).
